## Layout

```
norn/
  package.json        npm workspaces: module, module-test, bindings, workers, web (no package.json at the repo root)
  spacetime.json      database "norn", module-path ./module, server local, bindings go to ./bindings/src
  module/src/         schema.ts (tables), core.ts (hashing, baseline history, actors, policy gate, write(), reconcile), reducers.ts
  module-test/        the real module plus a failing reducer and policy rules; published only as the database "norn-test"
  bindings/           generated by `npm run db:generate`; committed so nobody needs the CLI to typecheck
  workers/src/        worker.ts, stages.ts + sim.ts (mock compute), seed.ts, checks.ts, checks-policy.ts, testkit.ts, spike/*.ts
  web/                Vite + React app; web/spike/*.mjs are the Playwright scripts
```

`npm ci` from a clean checkout took 23 s at this worktree's path (52 characters up to `norn`) with no esbuild `ENOENT`. Hoisting keeps `node_modules` one level deep.

## Commands

Run from `norn/`. `spacetime` must be on PATH (see Install).

```
npm ci                       # install (all workspaces)
npm run db:start             # SpacetimeDB on 127.0.0.1:3000 (foreground; keep a terminal for it)
npm run db:publish           # typecheck the module, then publish to the local database "norn", data kept
npm run db:reset             # same, but --delete-data=always (needed after a breaking schema change)
npm run db:generate          # typecheck, then regenerate bindings/src from the module
npm run test-db:publish      # publish the test module as the database "norn-test" (always wiped)
npm run test-db:generate     # regenerate module-test/bindings/src
npm run seed                 # 5 baseline assumptions, 3 fictional ECRs, 4 ECR assumptions, 3 parts, through the reducers
npm run worker               # a mock compute worker; WORKER_NAME=w2 npm run worker for a second one
npm run web                  # Vite dev server on http://127.0.0.1:5173 (?as=Alice sets the name, one identity per tab)
npm run typecheck            # tsc for module, module-test, workers, web
npm run build                # spacetime build + vite build
npm run check:module         # 48 rule checks against a live database (stop real workers first); NORN_DB=norn-test runs them on the test module
npm run check:policy         # 6 policy-gate checks, on norn-test
npm run spike:errors | spike:crash | spike:browsers | spike:streaming
```

Install on Windows: the documented one-liner `iwr https://windows.spacetimedb.com -useb | iex` did nothing in a non-interactive shell (it starts `%TEMP%\spacetime-install.exe`, which asks for confirmation in a dialog). `& "$env:TEMP\spacetime-install.exe" --yes` installed it to `%LOCALAPPDATA%\SpacetimeDB`. Open shells need that folder added to PATH by hand. `spacetime version list` shows `2.13.0 (current)`.

## What is in the schema (*revised*)

Tables (all public for now; snake_case in the database, camelCase in TypeScript): `principal`, `main_version` (append-only history), `norn_config`, `pull_request` (the ECR; has `kind` and a unique `plm_ecr_number`), `part` (unique `part_number`), `assumption`, `check_run` (stores `inputs_json` next to the hash), `check_progress`, `check_result`, `comment`, `action_log` (has `request_id` and `outcome`), `agent_event`, plus the private `reaper_schedule`. Who did something is stored as an Identity everywhere (`created_by`, `author`, `requested_by`, `claimed_by`); names are looked up in `principal`.

Reducers: `register_actor`, `set_config`, `create_pr`, `edit_pr_text`, `set_pr_status`, `add_comment`, `upsert_part`, `record_assumption`, `enqueue_check`, `claim_check`, `heartbeat_check`, `report_progress`, `complete_check`, `fail_check`, `record_agent_events`, and the scheduled `reap_expired_leases`. Every write reducer takes `meta: { requestId, spawnedBy }` first; `workers/src/connect.ts` and `web/src/rpc.ts` fill it in (`client.R.claimCheck({...})`). `add_commit` and the overlay tables (`Change`, `Commit`) are not built.

Errors a worker must tell apart start with a code: `[stale]` (inputs changed, discard), `[lost]` (the run is no longer yours), `[invalid]` (your result was refused). `classify()` in `connect.ts` returns it as `code`.

## Spike results

The scripts are in the repo and print the numbers below; spikes 1, 2 and 4 were re-run after the review changes.

**1. Worker claims, writes results, hits errors: pass.** `npm run spike:errors` (SDK clients standing in for workers; the deliberate failures run against the test module, `norn-test`).
- A `SenderError` thrown in a reducer reaches the caller as `SenderError` with the module's message. Any other exception (`Error`, `TypeError`) reaches the caller as `InternalError: "The instance encountered a fatal error."`; the real message and a source-mapped stack appear only in `spacetime logs` as `PANIC`. The next call after a panic took 1 to 3.7 ms, the same as normal.
- A failing reducer rolls back everything it wrote earlier in the same call, including its action-log row: checked for all three failure kinds, and for `complete_check` with a bad third result (no partial results, run still `running`).
- 20 races of two workers claiming the same run: exactly one winner each time; the loser gets `SenderError: check run N is running, not queued`.
- Fencing works: a second worker, a wrong attempt number, a finished run, and a run made stale by an input edit are each refused with a distinct message and code.
- The SDK separates `DisconnectedError` (never sent), `UnknownCallResultError` (dropped mid-call, may have run) and `InternalError`. `connect.ts` maps them to a retry policy: never retry a `SenderError`; retry `DisconnectedError` after reconnect; retry `UnknownCallResultError` only for idempotent calls; retry `InternalError` a few times. In the one in-flight disconnect I forced, the call had not run; I did not see a call that ran but reported unknown.
- Inside every row callback of one edit, the client cache already holds the whole transaction.

**2. Two browsers on one ECR: pass.** `npm run spike:browsers`, two isolated Edge contexts plus the worker.
- An assumption edit replaced only the checks that read it (Time to the line; Unit cost kept its run id), with no torn DOM snapshot on either screen; new revision on screen 58 to 92 ms after the click (includes Playwright's click overhead), recomputed and `done` about 1 s later. An edit after approval withdrew the approval in the same step. Two reviewers saving one assumption at once: one saved, the other got `'key' is at revision 4, not 3: someone else edited it`.
- Switching ECRs: subscribing to the new ECR first and dropping the old one when it applies leaves only baseline and the selected ECR in the cache after 4 slow and 4 rapid switches; the page never blanked or mixed rows (49 to 134 ms per switch). The stock `useTable` hook does the opposite order: 3 renders per switch, 2 of them empty or not ready. `web/src/store.tsx` has its own hook; the page keeps showing the previous ECR (dimmed) until the new one is applied.

**3. Streaming progress: pass, with one noisy run (not re-run after the review; the progress path did not change).** `npm run spike:streaming`. 40 of 40 updates (7 percentiles, 32 histogram bins) reached both screens in order in both runs. Run 1: lag from server timestamp to render p95 266 ms, max 349 ms (the worker's own round trips were slow in the same minute); run 2: p95 24 to 39 ms, max 57 ms. At about 20 reports a second: 400 of 400 reached both screens, p95 21 to 28 ms, max 179 ms, no main-thread task over 50 ms. Worker round trip p50 4 to 5 ms.

**4. Crash recovery: pass.** `npm run spike:crash`, workers killed with `SIGKILL`.
- Killed at 5,000 of 20,000 draws with a 4 s lease: back in the queue 4.8 s later (lease plus the up-to-5 s reaper tick), claimed by a second worker 2 ms later as attempt 2, finished 20 s later (it restarts from zero). One set of results, no leftover progress row. With `max_attempts` 1 the same kill ends as `failed` after 4.2 s.
- *New:* a stage that takes 7 s on a 2 s lease (standing in for an LLM call) finishes on its first attempt: the worker sends `heartbeat_check` when nothing else has touched the lease for a third of its length. Not run as a control without heartbeats.
- A worker running while I restarted the SpacetimeDB server reconnected by itself after about 20 s and the runs it lost came back through lease expiry. Not tested: a worker that is frozen rather than dead.

**5. Iteration speed: pass.** Add a trailing column with a default: publish 1.5 s, `db:generate` 1.7 s, typechecks 11 s. `db:publish` now typechecks the module first (publish step 6 s). A breaking change is refused in 1.6 s with a clear message; `db:reset` (6.6 s) plus `seed` (3.2 s). The catch is in rough edge 6.

**6. Hosting: not run.** The task said local only.

## What the new checks prove (*revised*)

`check:module` has 48 checks; each of these was shown to fail with its fix reverted (the module with the old behaviour restored, published as `norn-test`, checks run against it):
- **Chained hashes.** After finishing S1 and S2, an edit only S1 reads makes S2 stale and replaces S3 and S4; after an S3-only edit, a finished S5 goes stale while S2 and S4 stay done. Reverted: S2 stays `done`, S5 stays `done`.
- **Reopen.** A closed ECR reopened after another ECR was released is on the current baseline, with stage 1 keyed to the new BOM. Reverted: it keeps the old baseline.
- **Deep cap.** Three deep requests, each after an ECR text edit, all succeed (stale runs do not count); on the same inputs a failed run can be retried once and the third request is refused. S0 stays current through a baseline assumption edit and another ECR's release, and goes stale on a text edit. In automatic mode a new ECR gets each deep stage once, and edits queue no more; switching to automatic queues nothing on existing ECRs; a deep stage can never be enqueued as `automatic`. Reverted: the third request is refused, S0 goes stale, automatic mode re-queues.
- **Audit rows.** A baseline edit and a release each leave a log row on every affected ECR (including the withdrawal of the other ECR's approval). Reverted: no rows.
- **Blocked.** When S1 fails for good, S2 to S4 (and a requested S5) become `blocked` with the reason, cannot be claimed, and return to `queued` when S1 is requested again. Reverted: they stay `queued`.

The same run also covers: identity locking, `spawnedBy` per call and from the run, request ids, inputs stored on a run, the baseline history, PLM number and part number uniqueness, the agent event batch (out of order, resent), approval rules, edit conflicts, and a log row for every write reducer. `check:policy` proves that a denial returns normally and keeps its log row (matched by request id) without writing, that a downgraded approval is logged as `downgraded` and leaves the ECR in review, and that a downgrade with no weaker form becomes a refusal.

One guard has no check: a merge is refused when the ECR's base is behind the baseline. Every open ECR is moved onto the baseline whenever it moves, so the state cannot be reached through the reducers; the guard is defence in depth.

## TypeScript-module rough edges

1. **`tsc` is not found, and type errors still publish.** The CLI looks for `tsc` in the module's own `node_modules`; under npm workspaces it is hoisted, so `spacetime build` prints "tsc not found" and skips the check. `db:publish`, `db:reset` and `db:generate` now run `tsc` on the module first (4 s).
2. **A plain exception tells the caller nothing** (spike 1). Use `SenderError` for anything a caller can act on, and read `spacetime logs norn` when you see `InternalError`.
3. **A failed reducer rolls back its own log row,** so a denial that throws cannot be logged. The policy gate therefore returns normally on a denial and logs it (*revised*); only real errors vanish from the log.
4. **SQL is a subset.** One-off queries need `count(*) AS n` and reject `LIKE`. Subscriptions cannot compare an `Option` column to a literal. The worker subscribes to all running rows and filters on identity instead.
5. **A subscription filtered on state loses the row when the state changes.** Subscribe to the state you move into as well.
6. **A schema change drops every client, and a stale client crashes.** Adding a column closed all connections; the old client reconnected, parsed rows with the old layout, and threw `RangeError` from inside the SDK. After any schema change: regenerate bindings, restart workers, reload browsers. A code-only republish kept connections open.
7. **`spacetime.json` changes the CLI's positional arguments.** Pass `--no-config` for ad-hoc commands on another database (the `test-db:*` scripts do).
8. **Reducers return nothing.** A client that creates an ECR finds it by watching the table (the checks match on the title). A denial also returns nothing: the caller finds its outcome in `action_log` by the request id it sent.
9. **Only reducers may be named exports of the entry file.** Helpers live in `core.ts`; `index.ts` re-exports the schema as default and `export *` from `reducers.ts`.
10. **`spacetime start` listens on 0.0.0.0 by default.** `db:start` binds 127.0.0.1.
11. **Unique constraints are single-column** (`constraints` takes one column). The event key `(job, seq)` is therefore a string column `'<jobId>#<seq>'` that is unique.
12. **A second module in the same repo works by importing the first one's files** (`module-test/src/index.ts` re-exports `../../module/src/...`); the CLI bundles it and publishes under another name. Rules registered by a side-effect import (`POLICY_RULES.push`) run at module load.

## Design calls made (*revised*)

- **Review tiers (#10).** S1 to S4 are `code`, re-enqueued automatically whenever their inputs change. S0 and S5 are `deep`: they run only when requested, or once when an ECR is filed under config `deep_review_mode` `auto`; never re-queued after an edit, and never `automatic`. A deep run whose inputs changed goes stale and shows as outdated. The cap (`deep_review_limit`, 2) is per set of inputs: it counts requested runs on the current hash, failures included, so an ECR that keeps changing is never locked out of a review of its latest inputs. This is my reading of the review; #10's "once or at most twice per ECR" could also mean a lifetime cap, which would bring the lockout back.
- **Hashes chain.** A stage's hash covers what it reads itself plus the hashes of the stages it reads from. S0 reads only the ECR text. S5 reads only S2 to S4, so it goes stale when those do, which includes a baseline's BOM changing (S1 reads the BOM version). It no longer reads the baseline version directly. S1 keys on the BOM version: baseline assumption edits move the baseline version but not the BOM. The ECR's id stands in for the overlay until `Change`/`Commit` tables exist.
- **Baseline history.** `main_version` is append-only (`version`, `parent`, `cause`, `merged_pr_id`, `effectivity`, `at`, `by`, `note`). A release appends `eco`, a baseline assumption edit appends `assumption`. Every open ECR is moved onto the new version, and any whose inputs changed gets revision +1 and loses an approval. `effectivity` stays empty until the timeline stage can fill it.
- **Atomic edits.** `record_assumption` checks the revision the editor saw, writes the new row, marks stale runs and enqueues replacements in one transaction, with one log row per affected ECR.
- **Claims.** A worker names the run it wants; attempts increase on each claim and every later call carries the attempt number. Progress and heartbeats extend the lease. A scheduled reducer every 5 s gives back expired leases, or fails the run once `max_attempts` is used. A failed stage blocks the stages that read it, with the reason.
- **Identity (#34).** `kind` and `origin` are fixed at first registration (name and on-behalf-of can change). `spawnedBy` travels with each call; a worker's calls on a run say `check_run:<id>`. Unregistered callers are allowed and logged as `unknown`; an external agent must say whom it acts for. Not logged by design: no-op calls, lease extensions, progress ticks after the first, and agent events (each row names its actor).
- **Policy gate shape (#43).** `authorize()` returns allow, deny or downgrade with a reason; `write()` honours it. A deny returns normally and logs `outcome: denied`. A downgrade runs only where the reducer says it can (`set_pr_status` to `approved`, which logs `outcome: downgraded` and changes nothing); elsewhere it becomes a refusal. The real module has no rules; the test module registers three. The recommendation record is #43's.
- **Check runs store their inputs** (`inputs_json`): base version, code version, seed (code stages), the assumption ids and revisions, the upstream hashes.
- **External keys.** `pull_request.plm_ecr_number` is unique and required; an ECR filed in Norn gets `NORN-<id>` until the PLM assigns one (nothing relinks it yet). `part.part_number` is unique; only `upsert_part` writes it.
- **`agent_event`** matches PR #53's event shape: `seq`, `ts`, `jobId`, `role`, `identity` (as `actor`, `on_behalf_of`, `spawned_by`), `sessionId`, `type` (as `event_type`) and the rest as `payload_json`. Keyed by `(job_id, seq)`; a batch is idempotent. Nothing publishes to it yet.
- **Strings stand in for enums.** Bindings are committed. The UI says ECR, ECO, impact assessment, and labels every number and agent result `mock`.
- **Left for later, on purpose.** Random seeding for paired simulation (base and head must share draws) is #41's. The recommendation table is #43's. Also not built: the overlay tables, integration branches, a `CLAUDE.md` Commands block (other sessions own it).
