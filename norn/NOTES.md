## Layout

```
norn/
  package.json        npm workspaces: module, bindings, workers, web (no package.json at the repo root)
  spacetime.json      database "norn", module-path ./module, server local, bindings go to ./bindings/src
  module/src/         schema.ts (tables), core.ts (hashing, actors, action log, reconcile), reducers.ts, spike.ts
  bindings/           generated by `npm run db:generate`; committed so nobody needs the CLI to typecheck
  workers/src/        worker.ts, stages.ts + sim.ts (mock compute), seed.ts, checks.ts, spike/*.ts
  web/                Vite + React app; web/spike/*.mjs are the Playwright scripts
```

`npm ci` from a clean checkout took 23 s at this worktree's path (52 characters up to `norn`) with no esbuild `ENOENT`. Hoisting keeps `node_modules` one level deep.

## Commands

Run from `norn/`. `spacetime` must be on PATH (see Install).

```
npm ci                       # install (all workspaces)
npm run db:start             # SpacetimeDB on 127.0.0.1:3000 (foreground; keep a terminal for it)
npm run db:publish           # typecheck the module, then publish to the local database "norn", data kept
npm run db:reset             # same, but --delete-data=always (needed after a breaking schema change)
npm run db:generate          # typecheck, then regenerate bindings/src from the module
npm run seed                 # 5 baseline assumptions, 3 fictional ECRs, 4 ECR assumptions, through the reducers
npm run worker               # a mock compute worker; WORKER_NAME=w2 npm run worker for a second one
npm run web                  # Vite dev server on http://127.0.0.1:5173 (?as=Alice sets the name, one identity per tab)
npm run typecheck            # tsc for module, workers, web
npm run build                # spacetime build + vite build
npm run check:module         # 23 rule checks against a live database (stop real workers first)
npm run spike:errors | spike:crash | spike:browsers | spike:streaming
```

Install on Windows: the documented one-liner `iwr https://windows.spacetimedb.com -useb | iex` did nothing in a non-interactive shell (it starts `%TEMP%\spacetime-install.exe`, which asks for confirmation in a dialog). `& "$env:TEMP\spacetime-install.exe" --yes` installed it to `%LOCALAPPDATA%\SpacetimeDB`. Open shells need that folder added to PATH by hand. `spacetime version list` shows `2.13.0 (current)`.

## What is in the schema

Tables (all public for now; names are snake_case in the database, camelCase in TypeScript): `principal`, `main_version`, `norn_config`, `pull_request` (the ECR), `assumption`, `check_run`, `check_progress`, `check_result`, `comment`, `action_log`, plus the private `reaper_schedule`.

Reducers (the narrow API): `register_actor`, `set_config`, `create_pr`, `set_pr_status`, `add_comment`, `record_assumption`, `enqueue_check`, `claim_check`, `heartbeat_check`, `report_progress`, `complete_check`, `fail_check`, and the scheduled `reap_expired_leases`. `spike_fail` exists only for spike 1 and should be deleted before the demo freeze. `add_commit` and the overlay tables (`Change`, `Commit`) are not built.

## Spike results

Each line says what was run and what was seen. The scripts are in the repo and print the numbers below.

**1. Worker claims, writes results, hits errors: pass.** `npm run spike:errors` (SDK clients standing in for workers).
- A `SenderError` thrown in a reducer reaches the caller as `SenderError` with the module's message. Any other exception (`Error`, `TypeError`) reaches the caller as `InternalError: "The instance encountered a fatal error."`; the real message and a source-mapped stack (`spike.ts:16`) appear only in `spacetime logs` as `PANIC`. The next call after a panic took 3 to 3.7 ms, the same as normal (p50 3 ms for a reducer round trip).
- A failing reducer rolls back everything it wrote earlier in the same call, including its action-log row: checked for all three failure kinds, and for `complete_check` with a bad third result (no partial results, run still `running`).
- 20 races of two workers claiming the same run: exactly one winner each time; the loser gets `SenderError: check run N is running, not queued`.
- Fencing works: a second worker, a wrong attempt number, a finished run, and a run made stale by an input edit are each refused with a distinct message.
- The SDK separates `DisconnectedError` (never sent), `UnknownCallResultError` (dropped mid-call, may have run) and `InternalError`. `connect.ts` maps them to a retry policy: never retry a `SenderError`; retry `DisconnectedError` after reconnect; retry `UnknownCallResultError` only for idempotent calls; retry `InternalError` a few times. This is reliable enough to build on. In the one in-flight disconnect I forced, the call had not run; I did not see a call that ran but reported unknown.
- Inside every row callback of one edit, the client cache already holds the whole transaction (new revision, old run stale, new run queued, new assumption).

**2. Two browsers on one ECR: pass.** `npm run spike:browsers`, two isolated Edge contexts plus the worker.
- An assumption edit replaced only the checks that read it (Time to the line; Unit cost kept its run id). On both screens no DOM snapshot showed the new assumption with the old run, or the reverse (a snapshot is taken on every DOM change; React coalesces to one render per frame, so the SDK-level check above is the stronger evidence). New revision on screen 58 to 92 ms after the click (includes Playwright's click overhead); the worker recomputed it and both screens showed `done` about 1 s later.
- An edit after approval withdrew the approval in the same step on both screens.
- Two reviewers saving the same assumption at once: one saved, the other got `'key' is at revision 4, not 3: someone else edited it`.
- Switching ECRs: subscribing to the new ECR first and dropping the old one when it applies leaves only baseline and the selected ECR in the cache after 4 slow and 4 rapid switches; the page never blanked or mixed rows (96 to 134 ms per switch). The stock `useTable` hook from `spacetimedb/react` does the opposite order (React runs the effect cleanup, which unsubscribes, before the next subscribe): measured 3 renders per switch, 2 of them empty or not ready. So `web/src/store.tsx` has its own hook, and the page keeps showing the previous ECR (dimmed) until the new one is applied.

**3. Streaming progress: pass, with one noisy run.** `npm run spike:streaming`. Two browsers watch a Monte Carlo run of 20,000 draws, 40 reports with percentile (7 values) and histogram (32 bins) arrays.
- All 40 of 40 updates reached both screens in order in both runs. Run 1: lag from server timestamp to render p50 10 ms, p95 266 ms, max 349 ms (the worker's own round trips had a p95 of 94 to 260 ms in the same minute, so the delay was before the screen). Run 2 on the same data: p50 10 ms, p95 24 to 39 ms, max 57 ms. I do not know what caused the slow minute in run 1; it did not recur.
- At about 20 reports a second (400 reports, two streams at once): 400 of 400 reached both screens, p95 lag 21 to 28 ms, max 107 to 179 ms, no main-thread task over 50 ms. Worker round trip p50 4 to 5 ms, p95 11 to 23 ms. The UI is not the limit at this size.

**4. Crash recovery: pass.** `npm run spike:crash`, workers killed with `SIGKILL` (TerminateProcess on Windows, so nothing cleans up).
- Killed at 5,000 of 20,000 draws with a 4 s lease: the run returned to the queue 4.9 s later (lease plus the up-to-5 s reaper tick), a second worker claimed it 3 ms after that as attempt 2 and finished it 20 s later (it restarts from zero; there is no resume). One set of results, no leftover progress row.
- With `max_attempts` 1 the same kill ends as `failed` ("lease expired on attempt 1/1; giving up") after 4.2 s instead of looping.
- A worker was also running when I restarted the SpacetimeDB server (to rebind it to loopback): the worker's calls failed with `DisconnectedError` for about 20 s, it reconnected by itself, picked up queued runs, and the two runs it lost came back through lease expiry. Data survived the restart. Not tested: a worker that is frozen rather than dead.

**5. Iteration speed: pass.**
- Add a column with `.default(true)` at the end of a table: publish 1.5 s, `db:generate` 1.7 s, three typechecks 11 s, 14.5 s in all. Existing rows got the default, no data lost. `db:publish` now typechecks the module first, which makes the publish step 6 s.
- A breaking change (a column inserted before the last one, no default) is refused in 1.6 s with "Reordering table comment requires a manual migration" and "Adding a column kind to table comment requires a default value annotation". The way out is `db:reset` (6.6 s) plus `seed` (3.2 s).
- Reset plus seed: 9.8 s from a standing start. The catch is in rough edge 6 below: running clients do not survive a schema change.

**6. Hosting: not run.** The task said local only. The demo plan still needs a Maincloud deploy or a decision to demo on this laptop.

## TypeScript-module rough edges

1. **`tsc` is not found, and type errors still publish.** The CLI looks for `tsc` in the module's own `node_modules`; under npm workspaces it is hoisted, so `spacetime build` prints "tsc not found" and skips the check. A `const x: number = 'a'` published fine. `db:publish`, `db:reset` and `db:generate` now run `tsc` on the module first (4 s).
2. **A plain exception tells the caller nothing** (spike 1). Use `SenderError` for anything a caller can act on, and read `spacetime logs norn` when you see `InternalError`.
3. **A failed reducer rolls back its own log row,** so a denied attempt cannot be logged from inside the reducer that denied it. That matters for the policy work (#34): a denial log needs a reducer that returns normally after recording the refusal, or a separate path.
4. **SQL is a subset.** One-off queries need `count(*) AS n` (bare `count(*)` returns 400) and reject `LIKE`. Subscriptions cannot compare an `Option` column to a literal: `WHERE claimed_by = 0x...` fails with "cannot be parsed as type (some | none)". The worker subscribes to all running rows and filters on identity instead.
5. **A subscription filtered on state loses the row when the state changes.** The worker first subscribed to `status = 'queued'`; once its own claim made the row `running`, the row left the client cache and the worker waited for it forever. Subscribe to the state you move into as well.
6. **A schema change drops every client, and a stale client crashes.** Adding a column closed all connections ("WebSocket closed (code 1001: module exited)"). The old client reconnected, parsed rows with the old layout, and threw `RangeError: Tried to read 3840 byte(s)` from inside the SDK, killing the Node process. There is no "schema mismatch" message. After any schema change: regenerate bindings, restart workers, reload browsers. A code-only republish kept connections open.
7. **`spacetime.json` changes the CLI's positional arguments.** With it present, `spacetime describe other-db tables` reads `other-db` as the entity type. Pass `--no-config` for ad-hoc commands.
8. **Reducers return nothing.** A client that creates an ECR finds it by watching the table. The spike scripts match on the title; real code needs a client-supplied key.
9. **Only reducers may be named exports of the entry file.** Helpers live in `core.ts`; `index.ts` re-exports the schema as default and `export *` from `reducers.ts`. This worked once arranged, and is easy to break by exporting a helper.
10. **`spacetime start` listens on 0.0.0.0 by default,** with anonymous identities and every table public. `db:start` binds 127.0.0.1. Cal Hacks wifi would otherwise see the database.
11. `init` runs only on the first publish or after `--delete-data`, so a config key added later needs a fallback (`cfg()` in `core.ts` has one). Node on Windows prints `Assertion failed ... src\win\async.c` after an uncaught exception with a socket open; the first error above it is the real one.

## Design calls made

- **Review tiers (#10).** Each stage has a tier: S1 to S4 are `code` (re-enqueued automatically whenever their inputs change), S0 and S5 are `deep` (agent). A deep run exists only if someone requests it, or if config `deep_review_mode` is `auto` (Bowman's switch, set in the header). Requests are idempotent on the same inputs, and capped at `deep_review_limit` (2) per stage per ECR, counting stale ones. A deep run that goes stale is shown as outdated and not re-requested.
- **A check's hash is per stage.** Each assumption lists the stages that read it (`affects`), so an edit replaces only those runs. The ECR's id stands in for the overlay until `Change`/`Commit` tables exist.
- **Atomic edits.** `record_assumption` checks the revision the editor saw, writes the new row, withdraws an approval, marks stale runs, and enqueues replacements in one transaction. Editing the baseline (`prId` 0) does this for every open ECR.
- **Claims.** A worker names the run it wants (`claim_check(id)`); attempts increase on each claim and every later call must carry the attempt number. Progress calls extend the lease. A scheduled reducer (every 5 s) gives back expired leases, or fails the run once `max_attempts` is used.
- **Approval is of a forecast.** Approving needs every cheap stage done on the current inputs; any later input change sends an approved ECR back to review. Releasing an ECO bumps `main_version`, re-baselines the other open ECRs and cancels the released one's unfinished runs.
- **Identity (#34).** Every write reducer goes through `write()`, which resolves the actor from the `principal` table (filled by `register_actor`, self-declared until auth exists), calls `authorize()` (returns `allow (no rules yet)`), runs the body and writes `action_log` through `logAction()`: actor kind, name, origin (human, norn, external), on-behalf-of, spawned-by, policy, and the raw connection identity. An unregistered caller is allowed and logged as `unknown`. An external agent must say whom it acts for. Not logged by design: no-op calls, lease extensions, and progress ticks after the first (they would add 2 rows a second); `claim_check` and `complete_check` already name the worker.
- **Strings stand in for enums** (status, tier, trigger, source) and are validated in the reducers, because they read plainly in SQL and subscription filters.
- **Bindings are committed.** Regenerate with `npm run db:generate`; a schema change without it leaves workers and the web app on stale types.
- **The UI says ECR, ECO, impact assessment** (docs/GLOSSARY.md), labels every number and agent result `mock`, and shows who did what in the activity list.
- **No `CLAUDE.md` Commands block yet.** The repo's `CLAUDE.md` asks for one when the first package lands; the commands above are the content. I left `CLAUDE.md` and `README.md` alone because other sessions own them.

## Not tested

Maincloud, JWT or any real auth, policy denials (only the hook exists), more than a few hundred rows, a frozen (not killed) worker, Chrome or Safari, the production build served from `vite preview` (it builds; only the dev server was driven), real LLM workers (S0 and S5 sleep and return a labelled placeholder), `UnknownCallResultError` on a call that did run, and the overlay (`Change`/`Commit`), integration-branch and conflict tables.
